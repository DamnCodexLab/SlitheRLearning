# software/

Simulation and controllers for the Slitherbot snake robot. The robot models come from
[`hardware/description/`](../hardware/description): MuJoCo `.xml` and Isaac `.urdf`, generated by `make_description.py`.

```
software/
├── environment.yaml        conda environment for everything in software/ (Linux / WSL)
├── sinusoidal/             hard-coded serpenoid gait in MuJoCo
│   ├── run_gait.py         gait + simulation (summary / video / plot / interactive viewer)
│   ├── check_physics.py    physics sanity checks (see "Is the physics believable?")
│   └── results/            example runs: mp4 + plot per model
└── cpg/                    central pattern generator (coupled oscillators), same simulation
    ├── cpg.py              the CPG (no MuJoCo dependency)
    ├── run_cpg.py          drive the snake with it; --demo changes parameters mid-run
    └── results/            demo run: mp4 + plot
```

## 1. Environment (conda, in WSL / Linux)

```bash
conda env create -f software/environment.yaml
```

```bash
conda activate slitherbot-sw
```

After editing `environment.yaml`:

```bash
conda env update -f software/environment.yaml --prune
```

It contains Python 3.12, MuJoCo 4.0.1 (the newest release, Nov 2026), numpy, matplotlib, and imageio + ffmpeg for videos.

Rendering backends, set with the `MUJOCO_GL` environment variable:
- `MUJOCO_GL=egl`: headless rendering for `--video`. Works in WSL.
- The default (GLFW): opens a window. Needed for `--viewer`. Under WSL it uses WSLg.

Tested on WSL 2 Ubuntu 24.04 (CPU only; this machine has no NVIDIA GPU).

## 2. `sinusoidal/run_gait.py`: hard-coded forward gait

Every V (yaw) joint follows the same law as the browser gait viewer:

```
θ_i(t) = A · sin(2π f t + i φ) + bias        i = 0, 1, … over the V joints, tail → head
```

- **Direction:** with φ > 0 the wave travels from head to tail, which pushes the snake head-first.
- **Wheels:** the passive wheels roll freely along the body but grip sideways. That sideways grip is what turns the wave into forward motion.
- **H (pitch) joints** hold 0°. `--lift` can raise the head with the last H joint.
- **Start-up:** the gait fades in over the first second.
- **Servo updates:** targets are sent to the position servos at 50 Hz, the MG90S PWM rate.

```bash
python software/sinusoidal/run_gait.py
```

```bash
MUJOCO_GL=egl python software/sinusoidal/run_gait.py --video run.mp4 --plot run.png
```

```bash
python software/sinusoidal/run_gait.py --viewer
```

```bash
python software/sinusoidal/run_gait.py --model vh17_full --phase 60
```

| Option | Default | Meaning |
|---|---|---|
| `--model` | `vh9_full` | `vh9_full`, `vh9_bare`, `vh17_full`, `vh17_bare` |
| `--amp` | 30 | V joint amplitude A, degrees |
| `--freq` | 0.5 | wave frequency f, Hz |
| `--phase` | 45 | phase lag φ between neighbouring V joints, degrees |
| `--bias` | 0 | constant V offset, degrees. Nonzero makes the snake turn |
| `--lift` | 0 | head lift on the last H joint, degrees |
| `--backward` | off | reverse the wave (tail first) |
| `--duration` | 10 | simulated seconds |
| `--cone` | `elliptic` | friction cone, `elliptic` or `pyramidal` (see section 4) |
| `--video FILE` | – | record an mp4 that follows the snake |
| `--plot FILE` | – | png of the centre-of-mass path and joint tracking |
| `--viewer` | off | interactive MuJoCo viewer instead of a batch run |

Each run prints:
- distance moved forward and sideways, measured on the centre of mass
- steady speed, from the second half of the run
- how closely the servos follow their targets
- how often servo torque hits the MG90S limit

It also imports cleanly into other code: `SerpenoidGait`, `load`, `run` and `summarize`. That is the intended starting point for an RL environment, where the gait becomes the baseline.

### Results (10 s, A = 30°, f = 0.5 Hz)

| Model | φ | Forward | Speed | Max tracking error | Torque saturated |
|---|---|---|---|---|---|
| vh9_full | 45° | 2.33 m | 252 mm/s | 6.6° | 0% |
| vh9_full, `--backward` | 45° | −2.39 m | −253 mm/s | – | – |
| vh9_bare | 45° | 1.65 m | 181 mm/s | 3.9° | 0% |
| vh17_full | 45° | 2.21 m | 240 mm/s | **27°** | **12%** |
| vh17_full | 60° | 1.48 m | 165 mm/s | 5.6° | 0% |
| vh17_bare | 60° | 1.36 m | 150 mm/s | 14.9° | 4% |

`results/` holds the video and plot for vh9_full (φ = 45°) and vh17_full (φ = 60°).

What the runs show:
- **Forward and backward both work.** Reversing the wave reverses the motion at the same speed. With these settings the snake stays nearly straight: under 0.1 m sideways drift over 2 m, except the backward run, which drifted about 0.6 m.
- **vh17 at φ = 45° overloads the tail servos.** j03, j05 and j07 sit at their torque limit 35–70% of the time and lag up to 27°. With 9 V joints at 45°, the body spans more than one full wave, so the wheels fight each other. φ = 60° removes the overload and is slower but realistic. Use φ ≈ 60° for vh17.
- **Head lift slows vh9 a lot.** On the short snake, lifting the head 30° (the viewer's default) tips the body, so the H ribs and the caboose drag on the floor. Speed falls from 252 to 82 mm/s. That's why `--lift` defaults to 0 here. On vh17 the lift costs little.
- **Speeds are optimistic.**
  - The wheels grip sideways perfectly (friction 1.0, no compliance), so real speeds will be lower.
  - Masses and servo gains are still estimates, from `hardware/description/make_description.py`.
- **Simulation speed:** about 20× real time for vh9 and 2× for vh17 without rendering. Rendering video in WSL is much slower, about 0.1–0.2× real time.

## 3. Is the physics believable?

`check_physics.py` changes one physical condition at a time and checks that the simulation responds the way real physics says it should:

```bash
python software/sinusoidal/check_physics.py
```

```bash
python software/sinusoidal/check_physics.py --model vh17_full --phase 60
```

Results (6 s runs, all 8 checks pass on both models):

| Check | What physics predicts | vh9_full | vh17_full (φ 60°) |
|---|---|---|---|
| Free fall | The centre of mass accelerates at g | −9.810 m/s² | −9.810 m/s² |
| Weight support | Floor normal forces add up to m·g | 3.977 N = 3.977 N | 6.436 N = 6.436 N |
| No creep at rest | With servos holding still, nothing moves | 0.008 mm in 3 s | 0.008 mm in 3 s |
| **Frictionless floor** | Internal forces alone can't move the centre of mass (momentum is conserved) | 1.5 mm (vs 1321 mm normally) | 3.0 mm (vs 823 mm) |
| **Locked wheels** | Without rolling wheels, grip is the same in every direction, so the wave pushes much less | 26% of normal distance | 11% |
| **Coulomb sliding** | A wheel only slides sideways when its friction force is at the limit μ·N | sliding wheels at 100% of μ·N | 100% |
| Servo limit | Torque never exceeds MG90S stall, 0.176 N·m | peak 0.176 (clipped) | peak 0.139 |
| Time-step convergence | Halving the time step barely changes the result | 1321 / 1337 / 1347 mm (1.9%) | 823 / 820 / 821 mm (0.3%) |

The three bold rows matter most:
- **The motion comes from the floor.** Take the friction away and the snake goes nowhere.
- **It comes from the right mechanism.** Remove the difference between forward and sideways grip, and most of the motion disappears.
- **The sliding that remains is real Coulomb sliding,** not numerical creep.

More on the sliding:
- Wheels still slide sideways at 13–24% of their rolling speed. Contacts that slide are exactly at their friction limit, which is what Coulomb friction requires.
- Making the contacts stiffer, or adding MuJoCo's no-slip solver, barely changes the result. Changing the friction coefficient does. So the slip comes from physics, not from the solver.
- The cause is that a plain sine wave on the joints isn't a shape that wheels can follow perfectly. A real robot running this gait would slip the same way.

**What the simulation does NOT capture yet**, so trust trends more than absolute speeds:
- **Unmeasured parameters:**
  - The masses are solid-PLA estimates.
  - The wheel friction μ = 1.0 is a guess. Real PLA or TPU wheels on your floor need measuring.
  - Servo stiffness, damping and rotor inertia are guesses.
- **Idealised servos:** they are modelled as ideal position controllers with a torque cap and a speed estimate. Real MG90S servos have a deadband, gear backlash, sag as the battery voltage drops, and about 10–20 ms of control delay.
- **Rigid bodies:** no part deformation, and no backlash in the 3D-printed joints.
- **Cables:** the wiring harness's drag and stiffness aren't modelled.
- **Ideal floor:** perfectly flat with uniform friction.

These are the usual gaps between simulation and reality. The plan for them is to measure masses and friction, then randomise the remaining unknowns during RL training.

## 4. MuJoCo version and physics settings

We use MuJoCo **4.0.1** (Nov 11 2026), the newest release. 4.0.1 fixes a 4.0.0 bug that could make the Newton solver converge slowly or diverge.

What's new in recent releases, and whether it matters here:

| Feature | Release | Used? | Why |
|---|---|---|---|
| Elliptic friction cones (long-standing) | – | **yes**, the default here | The snake moves only because wheels resist sideways slip. With the elliptic cone plus `impratio = 10`, contacts creep less sideways than with the default pyramidal cone. On vh9: 252 vs 236 mm/s. |
| `mujoco.batch` thread-pool rollouts | 3.17 | not yet | Runs many copies of the model in parallel on CPU threads, with results bit-identical to a plain loop. The natural fit for parameter sweeps and CPU RL on this laptop. |
| Speculative contacts | 4.0 | no | Stops fast thin objects from passing through each other. Our contacts are slow wheels on a floor. |
| Elasto-plastic springs and flexes | 4.0 | no | For deformable bodies. Could matter later for a TPU skin. |
| MuJoCo Warp / MJX (GPU) | – | no | Needs an NVIDIA GPU. |

The model files keep MuJoCo's defaults, and `run_gait.py` switches to the elliptic cone when it loads them, so `hardware/description/` stays simulator-neutral.

## 5. `cpg/`: central pattern generator

A CPG produces the same travelling wave as the sine gait, but from a chain of coupled oscillators, one per servo. It's the amplitude-controlled phase-oscillator form of Ijspeert & Crespi (ICRA 2007), which Bing et al. (ICRA 2017) and Jiang et al. ([arXiv 2312.03223](https://arxiv.org/abs/2312.03223)) use on snake robots:

```
dθ_i/dt   = 2π f + Σ_j w · sin(θ_j − θ_i − φ_ij)      phase; j = neighbours in the same chain (V or H)
d²r_i/dt² = a · (a/4 · (R − r_i) − dr_i/dt)            amplitude → R, critically damped
d²δ_i/dt² = a · (a/4 · (B − δ_i) − dδ_i/dt)            offset → B (turning), critically damped
q_i       = r_i · sin θ_i + δ_i                        servo target
```

- **Two chains:** the V joints and the H joints form separate chains. Each has its own amplitude, phase lag and offset.
- **Shared and extra parameters:** the frequency is shared by both chains, and `head_lift` adds an offset to the last H joint.
- **Defaults:**
  - The V chain is set to the sine gait's values.
  - The H chain amplitude is 0.
  - Coupling w = 4/s and convergence rate a = 10/s, so the amplitude settles in about 0.8 s.
- **No MuJoCo dependency:** `cpg.py` is plain numpy. A `CPG` object is called with the time, like `SerpenoidGait`.
- **Changing parameters:** `set_params(...)` changes them while running.

```bash
python software/cpg/run_cpg.py
```

```bash
python software/cpg/run_cpg.py --random-phase
```

```bash
MUJOCO_GL=egl python software/cpg/run_cpg.py --demo --video demo.mp4 --plot demo.png
```

```bash
python software/cpg/run_cpg.py --viewer --demo
```

Options match `run_gait.py`: `--model --amp --freq --phase --bias --lift --duration --video --plot --viewer`. A negative `--phase` makes the snake go backward. `--coupling` and `--conv` set w and a.

**Checks (vh9_full unless stated):**

| | Result |
|---|---|
| Steady state vs. the sine gait | Joint targets identical, 0.000° max difference after 5 s. Speed 249 vs 252 mm/s, and vh17 at φ 60° gives 165 mm/s in both |
| Start from random phases | Phase-lag error 30° at 0.5 s, 1.4° at 2 s, 0.01° at 5 s. The coupling locks the wave by itself, and the snake still moves forward at 247 mm/s |
| Largest joint-target change between 50 Hz servo updates | 1.9° in steady running |

**The `--demo` run, the main reason to use a CPG:** the parameters change at 5, 10 and 15 s:
- 5 s: faster, amplitude 30→40° and 0.5→0.8 Hz
- 10 s: turn left, bias +10°
- 15 s: backward, φ +45°→−45°

| Segment | CPG | Sine, switched at the same instants |
|---|---|---|
| Forward | 250 mm/s | 252 mm/s |
| Faster | 387 mm/s | 387 mm/s |
| Turn left | turning +63°/s | +63°/s |
| Backward | 286 mm/s | 356 mm/s |
| **Largest target jump** | **7.3°** | **89.8°** |

- **Same gait, smooth switches:** both controllers walk the same gait, but the closed-form sine jumps up to 90° in one 20 ms update whenever the frequency or phase changes. A real MG90S would slam its end stop or brown out the supply. The CPG moves into the new gait over about one cycle. See `results/demo_vh9_full.png` (right panel) and `results/demo_vh9_full.mp4`.
- **Backward is slower:** the CPG's backward segment is slower because it spends part of the segment re-locking the phase lags to the reversed wave.

**Why this matters for RL** (the 2312.03223 recipe):
- The policy outputs a few CPG parameters (`freq`, `v_amp`, `v_phase`, `v_bias`, …) a few times per second, instead of 9 or 17 joint angles 50 times per second.
- The CPG turns every policy output, even a jumpy one, into smooth, wave-shaped servo targets. That suits CPU-only training and real servos.

## 6. Next steps

- **RL environment:** wrap `run()` as a Gymnasium environment. The simplest action is the CPG parameters (`CPG.set_params`) at about 1–2 Hz. The alternatives are joint targets, or a correction on top of the gait. The reward is forward speed, or progress to a goal.
- **Measurements:** measure part masses and servo response, and update `hardware/description/make_description.py`.
- **Physical calibration:** check sideways wheel grip on the real floor, then set `friction` in the model to match.
